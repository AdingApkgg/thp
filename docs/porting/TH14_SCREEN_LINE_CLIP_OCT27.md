# TH14 屏幕线段的半像素偏移与裁剪 · 2026-10-27

修正 C++ WebGPU 分支对屏幕坐标线段的处理：将半像素偏移放进裁剪前的坐标变换，并抵消宿主视口中对应的偏移。保留原有 1／256 取整，改动只作用于 Lines／LineStrip 的屏幕坐标分支。

实际 Application 第 2,265 帧原有 `(32,166)` 一个像素、R／A 两字节差异已消失，完整 1,228,800 字节与独立 D3D9 重放及冻结 GLES 输出相同。独立重放采用被观察的实际 C++ 输入和初始 GPU 颜色，不能称为原版普通游戏整帧。原版实际标题回读另有两帧重新验证通过，整作 1:1 未完成。

## 首差与对照

沿用[标题帧修复](TH14_NATIVE_TITLE_FRAMES_OCT27.md)后的共同启动 tick `474748194`、cookie `3457952651`、零输入和静音 sink。实际生产 Application 进入首个演示后的 240 拍，两个后端均为 2,265 帧、七项断言，131 行状态、文件和 1,508,352 帧静音 PCM 相同，画面却有两字节差异。

[观察准备工具](../../tools/th14-prepare-application-trace-oct27.py)的 `--process-host` 接入相同外部启动输入，只在私有 Renderer 副本中记录绘制前的语义参数。观察构建的完整画面与未插桩 C++ 基线逐字节一致，再将 192 个语义批次、实际 415 次绘制和七次清除交给[独立 D3D9 HAL 重放](../../tools/th14-application-trace-hal-oct27.py)。深度在使用前必须实际清除。

GLES 的 199 个语义／清除边界和最终画面全部与 HAL 相同。WebGPU 的首差出现在第 395 次绘制前后：目标 10 的 `(128,166)`，之后合成到屏幕 `(32,166)`。该绘制是一条屏幕坐标 LineStrip，原始 37 顶点、36 段，WebGPU 展开为 72 顶点。此前缓冲相同，R／A 的 HAL 与 GLES 为 `155/243`，WebGPU 为 `117/233`。

## 修复与结果

旧 WebGPU 用偏移后的视口实现半像素对齐，但屏幕线段已经在原齐次边界被裁剪，进入视口首个像素的线段因此丢失覆盖。仅取消坐标的 1／256 取整未解决问题，该负向实验保留。把半像素偏移移进裁剪前的坐标后，取消取整和保留取整的两个实验都与 HAL 相同；生产采用保留原取整的最小变更。

私有实验的全部 422 个实际绘制／清除边界均相同。随后重新编译实际生产 Application，未提供原版计算出的游戏状态或像素给引擎：

- 两幅演示前缀图像与冻结 GLES 相同，演示图像也与独立 HAL 的完整缓冲相同；状态、文件和静音 PCM 保持相同。
- 空闲计数 51／231 的 WebGPU 标题画面分别与实际原版第 240／420 次 Present 回读的完整 BGRA 缓冲相同，外部输入和两组 RNG 一致。
- 实际 C++ Renderer 的 21 组 Stage 参考、25,804,800 字节全部相同。

改动没有像素坐标特例，没有容差或 alpha 排除。原失败、原始命令、初始 GPU 颜色和实验均保留。原版标题采样所需的私有诊断代码、两次线程重定向及清理仍按前文声明；本项未启动原版游戏进程。
