# TH14 独立生产者恢复交付组件

本轮验证了不依赖录像帧号／VM 身份的独立交付通道：真实 Worker 在主线程同步 Wasm 执行期间，通知真实 `ReplayRngRestoreJobTh14` 执行三个存储。三次独立运行、取消和旧任务控制通过；捕获到的 12 次合成 RNG 调用经原版 x86 指令组件复算，48 个结果字全部一致，五次错误读取边界控制均被拒绝。

这不是普通 Application 的接入验收，也没有宣称原版 Windows 调度等价或整作 1:1 完成。正式玩法源码、Wasm 发布版本和模式通过数不变。

## 交付与对照

组件直接使用当前生产 `Rng.hpp` 和 `ReplayRngRestoreTh14.hpp`，没有改写 RNG 算法。独立 Node Worker 通过单独的 `SharedArrayBuffer` 只传操作就绪序号、提交确认和任务代次；它不知道 RNG 值、录像、帧号或 VM 身份。实际种子来自组件中的声明合成输入，三个存储由生产恢复 job 执行，提交后的确认才允许生产者发下一操作。

主线程始终停留在一次同步 Wasm 调用中，执行真实 `next32_with_boundary` 并轮询恢复 job。对照的同线程 60 ms 定时回调，在 120 ms 的同步调用内交付了零个存储，返回事件循环后才完成三个；独立 Worker 的三次运行均在同步调用返回前完成全部三个。实际交付落点不同，没有事先指定恢复必须发生在哪次读取前后。

取消控制在脚本种子存储后停止：只完成两个存储，玩法调用数清零没有执行，job 报告失败。旧任务代次控制在任何存储前失败。各例结束均释放观察 scope，Worker 正常完成／取消后被回收。组件不需要将 Wasm 线性内存改为共享内存，也未重编 141 个玩法对象；只编译一个小夹具和冻结四份生产头文件。

## 原版指令组件复核

捕获每个含恢复操作的合成 RNG 调用，包括调用前 seed／counter、实际读取保留值、返回值和结束状态。复核执行原版 `0x40332f` 起的算术主体及实际返回值拼接；在对应的读取前、读取后、计数提交后、写回前或写回后，执行原版 `0x456123` 的脚本种子存储指令。两线程寄存器上下文分开保存／恢复，主线程保留的输入不被晚到内存替换。

12 次捕获调用中，9 次来自独立 Worker 运行。返回值、结束种子、结束计数和保留输入共 48 个字均与未修改的 Wasm 记录一致。对五个含脚本恢复的调用，只把原版受控组件的写入移到读取另一侧，五个结果均与原 Wasm 调用不一致；没有向 Wasm 提供期望结果。这是组件负向控制，不是整局比较器的退出码验证。

原版 EXE 哈希仍为 `f08e885e…`。复核只在模拟器中执行声明的算术／存储／拼接主体，关键区入口按组件边界处理；未启动原版进程，未验证 Windows 调度、文件系统、GPU 或整局行为。

## 保留的初版与限制

初版通道六例逻辑通过，检查中发现 ACK 等待使用第二次读取作为 expected，可能在通知已发生后等待新值。修为复用使条件失败的那次读取值；取消同时改变等待字并通知。初版源码和结果保留，没有把约 100 ms 停顿唯一归因该窗口，也没有据此推断原版时间。

第一版原版核验器因 Wasm i32 导出在 JS 中表现为有符号数而拒绝比较：返回值相差恰为 `2^32`，其他三个字相同。失败和旧核验器留档；按 u32 位模式解释原有记录后通过，原始记录未改、独立线程未重跑。后续 driver 统一导出无符号字；已执行的冻结 driver 仍按原哈希保存。

通道等待真实主线程存储确认，带有尚未校准的额外同步成本。它只覆盖三个 RNG 存储，尚未接入普通 SDL／浏览器加载器，独立录像全局复制也未接入。下一步是以明确生命周期和取消边界接入真实 GameSession／资源宿主，再检查受影响完整记录；不能把这个有限组件写成独立调度、全模式或整作通过。

源码与入口为 `tools/th14-independent-rng-delivery-build-nov05.py`、对应 worker／check／native／evidence 工具，以及 C++ 同名夹具。[公开索引](th14-independent-rng-delivery-nov05.json)仅含统计、位置和路径／哈希，可用 evidence 工具 `--check` 复核。没有复制大资源，没有启动浏览器、原版或音频设备，也没有重跑已通过的 35,000 回调记录。
