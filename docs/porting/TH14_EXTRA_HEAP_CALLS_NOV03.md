# TH14 其他原版堆调用点

对原版导入表及调用指令核对发现，除先前跟踪的 `0x485583` 外，还有两个 `HeapAlloc` 调用点 `0x485538` 和 `0x494fbb`，以及 `HeapReAlloc` 调用点 `0x494ea5`。[独立指令组件](th14-extra-heap-sites-nov03.json)在合成系统调用边界确认了请求大小及参数，其中 `0x494fbb` 使用清零标志 8，`0x485538` 将零大小请求规范化为 1；并未执行实际系统堆。辅助观察器对 `0x485538` 记录的是规范化前的调用参数。

独立静音原版进程从调试附加后跟踪三个调用点至一面 600 个 Player 回调，记录到 [130 次清零分配返回](th14-extra-heap-trace-nov03.json)，均发生在观察器记录首个 Player 回调之前，涉及两个线程；其他两个调用点在该有限窗口没有被观察到。没有记录调试异常，音乐及音效主音量实测均为零。此次调试寄存器用于这些额外调用点，因此没有同时观察主要分配、共同释放或敌人工厂；不能将独立进程的事件直接合并为同一段堆历史。附加前的加载活动和其他系统调用仍未覆盖。

这些结果证明先前只跟踪 `0x485583` 的窗口遗漏了一类启动分配，但尚不能单独确定漏项对后续对象地址的影响，也不能声称复现原版堆或关闭 `worldZ` 差异。

随后在另一个静音原版进程中，同时跟踪主要分配返回、清零分配返回及共同释放入口，完成 [600 回调窗口](th14-combined-heap-trace-nov03.json)：分别记录 708、130、281 次事件，涉及六个被跟踪线程，未报告调试异常。按调试交付顺序，273 次非空释放均能与已观察分配配对，其中 89 次跨线程；其余 8 次释放入口的参数为空。此配对没有证明真实跨线程操作顺序，也没有证明释放成功。敌人工厂不在本次断点范围内，32 次 `0x530c` 请求只按大小筛选，不能单凭大小认定对象类型。

在这份同一事件流上，[两个隔离模型](th14-combined-heap-model-trace-nov03.json)分别排除及包含清零分配；两者对 32 次同尺寸主要分配的重用身份都匹配 25 次，相对第一个同尺寸请求的位置都匹配 1 次。模型只接收请求大小与按记录顺序配对的合成生命周期，不接收原版地址；实际交付顺序和释放成功在该实验中均是未经证明的假设。补充这 130 次分配仍不足以重现记录到的相对布局，不能将模型投入生产。

再将相同请求大小、清零标志和合成生命周期交给六个独立的 [x86 Windows 进程堆](th14-recorded-heap-windows-nov03.json)，每次的 32 个同尺寸请求相对位置也只匹配 1 次，重用身份匹配 23 或 24 次。助手进程没有接收原版地址；各自的进程启动堆与原版附加之前的堆状态不同或未知。该结果不能把差异唯一归因于候选分配规则，也不能证明哪一项未知因素是原因。
