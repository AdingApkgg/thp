## 当前工作的瓶颈

1. 原版实际进程捕获走吸引演示，3900 帧退出限制了长回归。分关窗口无法替代完整换关与整局。
2. GPU 独立候选过多。在完整原版回放基准未建立时，反复缩小少量像素差异占用了主线时间。
3. 普通输入控制器调参有助于取得自然录像，但这是测试素材生产，不等于移植核心的进度。
4. 现有大量单元证明不能自动相加成为整作等价；每次核心修改仍需要完整基准回归。

## 执行顺序与约束

第一优先建立 TH14 原版完整回放执行和不可覆盖的基准。先利用已验证的原版入口和真实进程初始化快照，列出每个宿主边界；原版游戏代码继续执行。未支持的调用必须停止并报告，禁止通用返回成功、修复栈或用候选结果补齐。只读快照启动本身不算整局通过。

随后建立快速原始 Demo 检查和长 Normal 六关检查，再扩大到六自机、难度与 Extra。只接受真实终止和有序换关；崩溃、预算耗尽或只捕获前缀统一标 INCOMPLETE。不能裁剪、重新同步、改 RNG 或让候选生成原版基准。

玩法完整回归稳定后，继续严格图像、音频、菜单、成绩及浏览器持久化验收。失败的 GPU 候选保留来源和数据，不进入生产渲染器，不把误差很小描述成像素一致。

先前核心的 Easy/Normal 咲夜 A 自然通关和移植内部完整录像回归已有通过记录；这些证据绑定各自版本，不自动继承到后续改动。原版不间断整局、完整图像、音频及浏览器存储验收仍未完成。详情仍以 CORE_STATUS 与各报告的实际范围为准。

## 新方法的实际结果

原版执行后端现与独立原版进程核对到3,901帧：每帧15组、64个状态字，共249,664字全部相同，包含玩法与视觉两个RNG。没有字段掩码、重新同步或库存/血量修改。通过版本固定在 `tools/th14-native-backend-reference-oct13.py`，独立检查报告为 `th14-native-backend-3901-verified-oct13.json`；后续实验在另一份提供器中进行，不能继承这个通过结论。

当前生产移植核心对同一基准的30个玩法字段无差异，7,802个启动视觉RNG字差异仍保留。原版后端会严格处理返回标题的请求，因此这3,901帧仍是吸引演示前缀，不是第一面通关或完整普通录像。

普通保存录像模式正在补齐启动与宿主服务。现有试验在暖启动快照执行原版的模式清理指令，显式记一处模式初始化；尚未覆盖真实菜单与加载器的完整启动链。符卡字体使用实际GDI栅格化，BGM读取只使用原始容器的只读字节，图形上传与静音设备服务均不作为图像/音频通过证据。每个未知接口保留失败收据后补齐明确协议，下一步仍是完整第一面与有序换关。

长基准已发现并修正一个生产缺陷：原版 MSG 构造函数 `4320b1..4320c4` 和 ECL 518 各做一次弹幕/激光/敌人清理，移植曾只保留后者。空掉落也调用 RNG，两次清理不能合并。第5,522帧原先少4次玩法RNG调用，并最终在原版第8,618帧GameOver；修正后8,618帧的30个玩法字段及捕获对象窗口无差异，启动视觉RNG差异仍保留。独立原版进程与执行后端的551,552个状态字一致，报告为 `th14-warm-replay-8618-constructor-clear-verified-oct13.json`。两份未改原始演示也各重跑3,901帧通过。

旧录像在原版不能自然通关，不能以移植自身的回放一致性当作原版整局证明。对话修正后的三条新普通输入路线都在五面GameOver，未计通过；下一步引入可追溯的真实原版长录像并继续固定基准回归，避免把主要时间用在自动控制器调参。

已引入 [ZPS 公开的原版录像](https://zps-stg.github.io/1cc.html)。来源称咲夜A Normal六关通关，结构验证确认六份关卡头/输入，但没有据来源描述直接标为本机原版整局通过。原始容器及208字节尾部完整保留，只在私有目录作数据输入。独立原版实际完成第一面9,669帧并进入第二面选择；执行后端618,816状态字完全相同，生产30玩法字段及对象窗口差0，视觉差异保留。后端在真实换关请求12处停止，仍为INCOMPLETE；当前生产整份播放则在四面GameOver，继续逐个真实分歧定位。第二面切片保留原关卡头与全部输入，用作独立定位，另行验证完整换关。

第二面已完成12,054帧独立原版切片对照，原始385,728字独立复算，30玩法字段及捕获对象窗口差0；视觉差异保留。其原版启动标志是44，必须在模式初始化后保留4，不能沿用第一面的40→0假设。后端换关严格按原版请求12的跳表分支 `446a8d` 执行真实析构/构造，目录服务仅虚拟化已捕获测试目录，不改宿主目录；遇到未知接口仍停下保存失败，而不是绕过生命周期。

第二面后端进一步核对771,456状态字，两个RNG也完全一致；第三面切片14,353帧的30玩法字段及对象窗口通过。原版后端的快速串行锁协议遇到 CRT 锁会拒绝并停止，新增服务只接受原版固定锁表中已初始化的条目，检查原始状态与所有权，未知锁仍拒绝。四面是当前真实长录像剩余失败区间之一，继续建立原版基准；这些分关结果不合并成不间断整局通过。

跨关定位已取得实际修复：第一面连续播放正确，但第二面第109帧先少4次玩法RNG调用；单独启动第二面却全程通过。检查原版 `44cc10`，发现 `44cdb7..44ce1d` 每次启动关卡都会按升序将256个自机子弹槽推到空闲链表头，`44d04e` 把伤害区域分配游标归零。移植先前只在构造时建池，跨关沿用了回收次序。现在执行同样的两步，保留原版没有清除的子弹/伤害记录，不按分歧结果调整RNG或库存。

修正后的连续生产录像在前四面53,288个已采样帧与独立原版分关基线的玩法RNG、分数、库存、自机与敌人计数一致；第二至四面的首帧pressed仍各有一处差异，视觉RNG差异与四个未采样换关末帧保留并明确报告。连续播放推进到五面、第72,316帧GameOver，仍不是六关通过。第二、三、四面完整切片对照已在当前源代码重跑，玩法及捕获对象窗口差0。第三面原版后端918,592字逐字相同。第五面原版基线正在建立，下一处差异仍须独立原版证据定位。

第五面19,052帧独立原版基线随后定位了第二个缺陷：原版117次发射的完整参数和减速倍率均与移植相同，自机碰撞边界也相同；但第15,899帧换外观后的首次绕屏不同，最终多保留13颗循环弹，16,458帧多擦弹并随后受伤。原版ETEX200在4186df调用46f520，绑定器46f637内部推进一次46fe50；此前把受控ANM单元边界的“不推进”误用于真实关卡。现在补回首次更新，外观尺寸在绕屏/退出检查前与原版同步。真实原版331帧弹幕16字段集合及26,793个发射输入字均独立复算无差异，证明来自原版数据，不靠修改碰撞阈值。

修正后前五面共72,344帧的分关30玩法字段及对象窗口通过；第五面原版后端1,219,328字与独立进程相同。连续播放推进到六面，在第89,957帧GameOver；前五面72,339个已采样帧仍保留首帧按键边沿、视觉RNG和未采样换关末帧。六面基线继续采集，不将五面通过当作整作完成。
