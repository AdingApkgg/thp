# TH14 shared camera right-vector publication — 2026-11-12

The shared world camera now publishes its unnormalized right X/Y in one aligned 64-bit atomic store, then right Z in one 32-bit store. Normalization still publishes X, Y and Z as three separate 32-bit stores. This preserves the original write granularity and order while retaining the existing independent 75-word camera reader.

Original `446590` writes an eight-byte XY pair; `44659d` writes Z; the selected original D3DX implementation then writes normalized X/Y/Z at `101bcaa0/101bcaa4/101bcaa9`. The retained original instruction-write trace is revalidated against the current executable and DLL instruction bytes. Its arithmetic and physical scheduling are not accepted from Unicorn. Independent original-host math fixtures provide the numerical reference instead.

The old optimized SDK object writes raw Y and then X as two scalar stores. The new optimized SDK and browser objects each contain the aligned `i64.atomic.store` branch followed by scalar Z and normalized X/Y/Z publications. The 32 existing matrix stores retain their previously verified order. This is a publication-protocol correction; it does not prove the cause of the previously observed cached-matrix or full-image differences.

The original shared world camera at `0x4d9190` has an eight-byte-aligned right pair. Intel documents atomicity for naturally aligned eight-byte accesses in [Guaranteed Atomic Operations, section 7.1.1](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366821.pdf). WebAssembly atomics require natural alignment; misaligned atomic accesses trap, as described by the [WebAssembly threads specification](https://github.com/WebAssembly/threads/blob/main/proposals/threads/Overview.md). Accordingly the C++ shared world-camera owner explicitly enforces eight-byte alignment. SceneCamera remains 300 bytes, and SceneCompositor's measured size remains unchanged while its alignment becomes eight. Other unaligned private cameras use an ordinary qword fallback; atomicity is not claimed for that fallback. The production asynchronous camera readers use the aligned world-camera owner. No entire-camera atomic snapshot is introduced, and separate ordered reads can still produce a mixed camera.
