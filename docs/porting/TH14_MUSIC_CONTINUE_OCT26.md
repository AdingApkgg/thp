# TH14 实际续关音乐队列与首曲恢复修复 · 2026-10-26

续关音乐现在按原版完整命令链路确定恢复前的文件状态，替换此前首曲负寻址时保留旧解码位置的回退。原版 `44aef0..44af2c` 先经 `46ef90` 请求保存的文件名，并等待 `46e5e0` 消费队列；其间 `481a60` 清除 reader `+9c` 循环标志，`480cf0` 填满新曲目的流式缓冲，之后才调用 `481ee0` 恢复保存的时间。

因此，首曲不足一 PCM 帧的有符号 seek 虽然失败，保留的是刚由选曲队列建立的文件位置。对于实际 TH14 布局，该位置在曲目开头四秒处。实现从原始布局和缓冲大小计算它，再以原版无符号剩余字节数继续跨曲目读取，最后回到当前曲目的循环起点；不直接使用原版输出作为运行时输入，也不填入猜测的静音。

[生产混音对照报告](th14-music-continue-verified-oct26.json)记录：

- 原版实际续关音乐窗口、队列写入与消费、文件名查找、布局重置、缓冲重建／填充、播放及最终恢复均在 x86 执行器中运行，原指令不修改。COM、计时和通知游标为声明的受控边界；文件服务使用真实 Windows 只读调用。
- 18 个恢复文件名、6 个精确纳秒时间、结果音乐此前 0／128 次通知，共 216 个完整音乐队列用例。进入最终恢复前，布局和 reader `+9c=0` 一致；最终原版 PCM 与对应独立恢复用例一致。
- 全部 108 个恢复／补帧用例通过，共 410,218,200 个归一化浮点样本字；包括此前排除的 4 个首曲用例。18 个零时间长段覆盖文件范围交界和当前曲目的循环。
- 原有 180 个正时间、暂停和全局挂起的时钟前缀继续一致，共 298,224 字；保存前用非整块推进，检查旧缓存不会掩盖定位。18 首同曲重开、静音、暂停、丢弃及每首 190,000 帧的分块独立性检查继续通过。

另一个独立的受控实验比较了单独 `481ee0` 调用前的 12 种读取历史：未循环时，失败 seek 会保留不同旧文件位置；循环后，`481880` 会先 seek 到 intro。这说明单独恢复函数的旧上下文不能直接代替实际续关队列的上下文。这里采用的是完整续关队列证据。

生产 Web 模块重编译音频对象，复用其余 145 个绑定对象，导入和导出一致；[运行包范围](th14-launcher-site-music-continue-candidate-oct26.json)仍标记为未通过实际浏览器验收。测试使用静音 SDL 替身，没有打开音频设备或播放声音，比较过程不保留整段浮点输出副本。

这些结果不证明队列播放与最终恢复之间发生物理通知竞争时的行为、设备队列、完整 Application 续关的玩家／HUD 状态、浏览器播放或整作音频等价。`completeGame=false`、`nativeEquivalent=false` 保持不变。[上一版本](TH14_MUSIC_SUBFRAME_OCT26.md)的 104 用例报告作为历史范围保留。
