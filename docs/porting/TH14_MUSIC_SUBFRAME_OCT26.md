# TH14 音乐恢复的有效寻址与缓存修复 · 2026-10-26

本页保留 `939b834` 的历史范围。后续[实际续关队列修复](TH14_MUSIC_CONTINUE_OCT26.md)已补齐当时排除的 4 个首曲用例；下文的“当前”指该旧版本。

保存的音乐时钟不足一个 PCM 帧时，原版 `481ee0` 将帧数截断并减去一帧，`481b40` 再以 32 位无符号算术计算文件偏移。原有移植版在这些时间点保留旧解码位置。当前修复根据原始音乐布局，把 17 首曲目的有效文件偏移映射到已有的无损 FLAC，跨曲目连续读取，到当前曲目结尾后回到其循环起点；不增加原始音乐资产。

首曲的特殊情况继续保留未完成标记。它产生的偏移作为 Windows `SetFilePointer` 的有符号距离传入后，调用会失败并保留原文件位置；该位置取决于先前的 DirectSound 填充与通知。初版实验适配器错误地把这个请求当成无符号文件尾寻址，得出了“先静音四秒”的结果。真实 Windows 只读调用已否定这一结果，相关候选被撤下，未作为源码发布。当前首曲仍保留先前解码器回退，不声称等价。参见 [Microsoft 接口定义](https://learn.microsoft.com/zh-cn/windows/win32/api/fileapi/nf-fileapi-setfilepointer)。

另一项实际修复是清除重新定位前的混音缓存。`ma_sound_seek_to_pcm_frame` 会留下已经预解码的样本；原版恢复则重新创建流式缓冲。现在支持的恢复和同曲重开会重建混音节点，避免先输出旧位置的一小段 PCM。其他作品的条件编译语法检查通过。

[生产代码对照报告](th14-music-subframe-verified-oct26.json)记录：

- 原版整段 `481ee0`、`480cf0`、`481620`、`481b40`、`481c40` 在 x86 执行器中运行；文件服务调用真实 Windows 只读接口，COM、计时、锁定及通知游标为声明的受控边界。
- 18 首、108 个原版恢复输入中，明确排除首曲的 4 个不足一帧用例；其余 104 个用例的 389,711,700 个归一化浮点样本字一致。17 个零时间长段覆盖跨曲目边界和当前曲目循环。
- 原有正时间、暂停与全局挂起的 180 个原版时钟前缀继续一致，共 298,224 字；保存前另用非整块样本推进，检查预解码缓存不会掩盖定位。
- 18 首的同曲重开、静音、暂停、丢弃和每首 190,000 帧的不同分块方式检查通过。静音按浮点零判断，允许正负零。

采样比较流式计算哈希，不保留约 1.56GB 的浮点输出副本。生产混音器接入静音 SDL 替身；测试没有打开音频设备或播放声音。Web 模块复用 145 个绑定对象并重编译音频对象，导入和导出保持一致；[打包范围](th14-launcher-site-music-subframe-win32-candidate-oct26.json)仍标为未通过实际浏览器验收。

上述结果不证明首曲负寻址、物理 DirectSound 通知时序、设备队列、实际 Application 续关、浏览器播放或整作音频等价。`completeGame=false`、`nativeEquivalent=false` 保持不变。

复核工具为[原版执行器](../../tools/th14-music-subframe-native-oct26.py)和[生产混音器比较](../../tools/th14-music-subframe-check-oct26.mjs)。依赖本地原始文件、既有无损音乐及哈希绑定的私有构建对象；这些输入不随源码发布。
