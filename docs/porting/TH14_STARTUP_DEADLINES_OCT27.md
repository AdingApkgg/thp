# TH14 启动任务到期时钟与严格标题样本 · 2026-10-27

修正原生组件测试宿主的通用计时：任务按各自排队到期时间交付，后续任务从该时间继续排队；每个 Application 帧仍从固定 60 Hz 边界开始。旧宿主把所有到期任务的时钟统一推到下一帧，额外推迟了任务链。最短回调延迟仍为 1 ms，没有按游戏任务类型分支，也没有更改生产 C++ 或浏览器调度器。

这是声明的外部平台模型：回调执行时长为零，回调只在实际 C++ tick 之前交付。它不能重现原版任意线程交错。原版另一份启动记录仍失败，不能由本次有限通过宣称整作 1:1。

## 严格通过范围

同一份生产核心，采用原版观察到的外部初始 tick／进程 cookie。实际原版第 420 次 Present、标题空闲计数 232，与两个后端的实际 Application 第 415 帧进行比较。

| 内容 | GLES／WebGPU 结果 |
| --- | --- |
| 80 次动画发布的句柄、文件、脚本及顺序 | 全部相同 |
| 30 个活动 VM，各 303 字及注册链顺序 | 全部 9,090 字相同 |
| 两组 RNG 的种子和调用次数 | 相同 |
| 完整 BGRA 后缓冲，包含 alpha | 1,228,800 字节相同，零容差 |

没有按文件／脚本重新配对，没有映射句柄，没有写回状态、补 RNG 或改参考图像。原版发布顺序由硬件断点观察；C++ 创建记录在调用入口保留记录位，子对象可先发布，因此按实际句柄序号恢复发布顺序。测试夹具只增加只读的 `component_births` 导出，最多观察 4,096 条创建记录。

这关闭了这份启动历史中的严格句柄差异。此前旧宿主下的 61 项失败报告继续保留，其有限结果绑定原来的工具和版本，不改写为通过。

## 保留的另一种启动交错

另一份实际原版第 210 次 Present／空闲计数 20，原版有 56 次发布、脚本 RNG 调用 1,316 次。相同外部启动输入下，当前通用到期模型仍有 57 次创建、脚本 RNG 调用 1,340 次。虽然完整图像相同，这个样本仍严格失败。

原版资源泵与 worker ready 边界的观察表明，工作线程可以在主资源泵和同帧加载动画绘制之间发布完成标志。私有诊断中仅将 `TitlePublish` 零延迟回调放到同次交付能够匹配这一份记录，但这种任务类型特判没有进入公共宿主或生产代码。还需解释真实的交付时机，不能挑选一种原版历史代替所有启动情况。
