从普通回放列表启动时，生产 `GameSession::activate_stage` 一直把初次创建参数传为 `true`，使脚本／动画 RNG 沿用此前标题页状态。现在 TH14 按实际模式选择参数：首次演示保留该状态，普通回放首关恢复录像种子。玩法 RNG 的种子恢复及计数清零沿用原实现，脚本 RNG 的调用计数继续保留。

## 原版指令与实际 C++ 控制

[原指令工具](../../tools/th14-initial-replay-restore-native-oct27.py)使用已保留的 KMK 魔理沙 B Normal 录像，来自 [Royalflare 档案](https://maribelhearn.com/royalflare/th14)。输入 SHA256 为 `28d9d29a34cf1dd0e67d67a82c1f0a5f7c508543271e0f1b1e4cbed527ff7353`；本轮未下载新的录像。

六个原始关卡头、四个初始脚本种子、两个初始玩法种子、两个调用计数和三种带位 2 的标志，共 288 个声明的虚拟 ABI 输入控制。执行实际 `435ed0 → 435f32 → 456050`，停在真实返回位置 `435f37`。每组核对两次种子写入、一次计数写入和全部 28 次复制的地址、PC、宽度及值；保留字也逐位核对。原指令没有修改，没有启动原版进程。首次试图执行到 `435f50` 包含未建模的 HUD／相机调用，失败保留，不能算原版普通菜单验收。

[C++ 比较工具](../../tools/th14-initial-replay-restore-compare-oct27.py)直接编译生产 `Replay.cpp` 的恢复函数，以及[观察夹具](../../runtimes/th12/th12_web/tests/cpp/th14-initial-replay-restore-fixture.cpp)。核对四个 RNG 字和 22 个映射的经济状态字。按旧调用参数为 0／288 相同，全部差异仅在脚本种子所在的第一个字；按修正参数为 288／288 相同。调用参数还绑定实际 `GameSession.cpp` 源码，但这个组件本身没有编译或对照整个 GameSession，不能扩大其范围。

随后实际重编译 `GameSession.cpp` 和注释更新的 `Replay.cpp`，校验复用 139 个未变核心对象，重链接真实 Application／设备。初次重链接预检查因旧清单中的 GLES 着色器头变化而拒绝；后续遍历全部 141 个核心源及夹具的真实包含图，确认两个变化的 SDL 头均未参与这些对象，才更新未使用头的清单。原始拒绝记录保留。

## 实际菜单回放仍失败

新的真实 C++ Application 经普通归一化菜单键打开同一录像，在实际 GLES 渲染和静音音频队列上运行。要求六面实际入口、自然结束、录像声明的最终得分以及结束后稳定 60 帧。原录像保存元数据的 reached 为 8、得分为 61,284,943 单位；这些元数据不是原版播放或通关证明。

该测试未通过：总共运行 27,251 个 Application 帧，保留 8,434 行日志；二面残机耗尽，实际所见得分 3,285,179 单位，等待三面入口的断言失败。此前已有 20 项场景断言通过，但没有观察到三至六面，也没有到达最终得分检查。首关种子修复不能唯一解释旧暖启动记录的提前结束，不增加现有 30／25 模式覆盖。

首次完整测试在执行前因场景各段上界之和超过声明总预算而拒绝。后续单独声明每面等待上限为其记录输入长度加 6,000 帧，场景上界合计 129,854，仍在 150,000 帧／3,600 秒预算内；输入、生命、血量及关卡没有强制修改。两份失败均保留。测试保留 100 GiB 空闲保护及 128 MiB 输出上限。
