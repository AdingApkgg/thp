2026-10-30。整作 1:1 未完成。本次只修改共享 Launcher 的 `manageReplays`，TH14 C++／Wasm 与原作资源不变。

实际 Chrome 中，管理器先打开窗口、再启动既有 iframe 时，Runtime HTML 返回 200，子文档仍停在 `about:blank`，最终读取超时。同一包经不打开窗口的普通“下载录像”入口则加载了 shell、Wasm 和资源，并显示已开始下载。这个提示只证明导出流程返回，未证明文件下载字节。

把隐藏 Player 临时设为有布局、读取过程中关闭模态窗口、使用非模态加载窗口，均未解决留存的超时；这些候选已撤除。修改生产函数，在 TH14 尚未 ready 时先等待 `ensureRuntime(false)`，就绪后再打开原管理窗口；期间切换作品则不打开旧窗口。其他作品及已就绪路径保持原顺序。

随后同一包实际列出 `th14_01.rpy / 0.5 KiB / 1 个文件`。将正式源码剥离类型后覆盖到冻结预览，再在同一浏览器的新标签页冷启动，重复读到同一文件。源码、实际服务的 app 模块、未变的 Wasm、两幅私有截图及 HTTP 观察均由[公开哈希元数据](th14-replay-manager-startup-oct30.json)绑定。这个结果接受本次实际文件列表读回，不推导所有浏览器的统一原因，也不把最小 iframe 控制的成功改写成失败。

[验证／预览工具](../../tools/th14-replay-manager-startup-oct30.mjs)运行真实生产函数的修复前后 14 项声明 I/O 控制，检查冷启动顺序、已有运行页、其他作品、原错误保留、列表错误及切换作品；它们不是原浏览器导航的模拟证明。工具另外确认源文件仅该函数改变，冻结旧函数与声明基线一致，再生成只覆盖这个函数的预览。
