# TH14 加载 flags4 对照与测试生命周期修正

2026-11-13。游戏实现仍为 `84b8741af5b7ca617cc4046fe697d3cbfebbf4ad`。本次修正对照夹具，未修改游戏代码或重发运行包；加载尾部 24 次 SCRIPT 差异和整作 1:1 仍未关闭。

## 首差来自夹具所有者失效

新增六组实际原版 ASCII17 加载序列，覆盖 flags4 的保持、解除、结束中断先后与 0.5 速率。最初一组从第 1 帧起出现 90 帧、441 字差异，早于结束中断。只读地址观察发现：主计时器已经引用新管理器，ASCII14 的透明度插值计时器仍引用已销毁的模板准备管理器。加入只读诊断后分配历史改变，失败组也随之改变；两个失败结果均保留。

另用两个同时存活的管理器排除单纯释放内存的影响：模板由速率 1 的管理器准备，运行管理器速率 1 时五组一致；运行速率 0.5 时有 75 帧、302 字差异，插值仍引用准备方。这证明跨管理器复用的速率引用问题，但当前 Application、GameSession 和资源入口均把准备与执行交给同一个会话动画管理器，尚未观察到生产路径跨管理器复用。不能将该组件现象直接宣称为生产加载 RNG 的原因，也没有据此修改核心复制规则。

修正夹具后，在销毁准备管理器之前释放其模板；每组先按原版 Oracle 的速率 1 准备模板，再切换到该组执行速率。所有原版脚本、初始 RNG、更新次数、中断和标志序列均保持。新六组共 966 帧、2,072,862 字全部一致。原七组也用修正夹具复核：1,127 帧、855,162 字全部一致。故意忽略 Control 标志的负对照在三组中仍产生 28,410 个错误字。

六组新原版记录实际只覆盖速率 0.5 和 1；其继承报告里的 `rateValues` 静态列表不能用作覆盖证明。旧七组另覆盖 0 和 1.5。全部比较使用各活跃 VM 的 303 字表示、原始句柄、注册链和两组 RNG，不归一化。303 字表示不等于整个原版对象，新增 rotation-Z 插值扩展也不在这份表示中。
