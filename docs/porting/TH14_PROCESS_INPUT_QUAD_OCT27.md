# TH14 进程输入控制与 GLES 四边形修复 · 2026-10-27

本轮补齐 GLES 非实例化四顶点 Strip 的投影取整处理。此前只有三角形及实例化四边形启用已有的完整图元判断，同一实际 Application 第 2,264 帧因此仍有 8 像素、10 个通道字节差。

新增[实际批次回放工具](../../tools/th14-application-gles-trace-oct27.py)及[诊断夹具](../../runtimes/th12/th12_web/tests/cpp/th14-application-semantic-trace-fixture.cpp)。夹具仅开放私有调用的诊断访问，保留实际 C++ Renderer、192 个语义批次和 35 组实例数据。修复前先完整复现未经观察钩子的 GLES Application 缓冲，然后与留存的独立 D3D9 绘制哈希逐批比较。

首差是第 149 次绘制、事件 262、目标 9、BGRA8 纹理 99：绘制前完整缓冲相同，绘制后出现 10 像素、15 字节差。自有隐藏 D3D9 设备另存第 148／149 次完整颜色、实际 ProcessVertices、关闭混合／深度的浮点源片段和 UV。关闭 UV 观察后的原生整帧哈希不变；GLES 浮点目标的源片段与 UV 已有差异，不能归因于之后的混合取整。首次未处理深度资源及有符号清除字的回放失败、一次编译临时目录错误、UV 观察的 ctypes 签名错误均保留，不计入通过。

实际状态是非实例化 `Strip/count=2`。生产 GLES 当时把它的投影资格设为零，而同一 C++ 判断在 WebGPU 路径和实例化四边形路径为真。私有单项实验修正后，全部 199 次语义绘制／清除后的完整缓冲哈希与独立 D3D9 相同。正式代码随后应用同一处理，重新编译的实际 C++ 组件再次通过；未经诊断钩子的当前完整 Application 也生成相同的 1,228,800 字节。没有加入坐标特判、像素容差或 alpha 排除。

## 同一外部输入下的完整演示

此前两后端各完成 17,545 帧，但过程日志与音效哈希不同。Application 构造器通过 `std::random_device` 获取进程 cookie，配置本作已有的栈回退模型。旧运行没有记录该输入，不能据新实验唯一归因或改写旧失败。

[输入准备工具](../../tools/th14-prepare-application-cookie-controls-oct27.py)只在冻结的原生单元宿主中声明这次 WASI 熵输入：构造器请求的唯一一个四字节缓冲，在游戏回调之前获得明确值。实际 C++ cookie 默认逻辑、游戏 RNG、时钟、演示和后续碰撞状态均未修改。

同一个旧 GLES 二进制分别收到 `0xbb40e64f`／`0x4b000000` 后，各 11,220 帧、16 项断言完成；日志分别 2,714／2,715 行，末尾分数 653433／653434，实际静音 PCM sink 各 8,057,856 帧的哈希不同。这证明该外部输入在当前移植模型中会改变状态及音效，不证明原作所有 ABI 行为已闭合。

修复四边形之前，在声明相同 cookie 后，完整三次演示的全部 4,239 行日志及各 12,681,216 帧静音 PCM 累计哈希已相同，画面仍保留十字节差。更早 11,220 帧共同输入前缀的 GPU 运行在最终磁盘检查失败；其已留存日志和音效相同，但该运行依旧是失败。

正式四边形修复后，两后端分别重新构建并再次完成三段演示和返回标题：各 17,545 帧、30 项断言、13 项动作，全部 4,239 行日志、七份共 8,601,600 字节完整画面以及各 12,681,216 帧静音 PCM 累计哈希一致。新 WebGPU 二进制与旧版不同，重新执行完整回归，没有把旧报告直接继承给新构建。旧未记录 cookie 的负向诊断、修复前的画面失败和存储失败继续保存。
